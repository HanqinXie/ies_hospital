## UPS 的聚合电平衡证明

逐段记 `S` 为非 UPS 实源，`U` 为 UPS 放电，`B01/B23` 为 P0/P1 与 P2/P3 实际建筑电，`P` 为所有实际厂站电，`C` 为 UPS 充电。共享求解器已有：

```
S + U = B01 + B23 + P + C
0 <= U <= B01
```

所以 `B23 + P + C = S + U - B01 <= S`。EC、ABS、锅炉、GT starter、储冷泵和恢复端口均进入 `P`；建筑风机/输配泵已在 `B01/B23` 中。UPS 不可能经聚合电量间接支付厂站负荷。需要保留的不是额外多余物理约束，而是这个已有约束组合和实际反例。

本轮实际短端口：P0 建筑电 10 kW、关键冷 10 kW，EC 已到达正许可，非 UPS 实源全部为零、UPS 端口 160 kW。`test_building_only_ups_cannot_indirectly_pay_ec_main_power` 通过：建筑电可供，EC 冷量与关键冷交付为零。`audit_supply()` 对实际已结算 action 提供逐厂站端口审计，不作命令投影或自动修正。

## DC 请求、实际启动与失败

旧调用链为 `ExecutionRecoveryCore._update_support_states()` → 新的 `diesel_start_minute` / `STARTING` → M22 `boundary()` 对新实际启动身份记一次。发动机本地自启动与上层到达的 DG 电端口上限分开：上层零电上限不会许可 DG 供电，也不等于撤销已触发的本地发动机启动。没有借本轮诊断增加或取消该本地权限。

| 情况 | 既有执行含义与 V23 有限账要求 |
|---|---|
| 排队/取消尚未开始的上层命令 | 命令本身不 claim DC；纯 `request(False)` 清 pending，不扣次数 |
| 实际开始后失败或被终止 | 新 `diesel_start_minute` 已对应一次实际尝试，资格已消耗；失败清启动时钟，不退还资格 |
| DC 缺失期间请求 | 不能开始，不消耗尚未发生的启动 |
| DC 硬件恢复 | 仅恢复路径条件，原窗口终点和 used 不动 |
| 第三次请求 | 已用两次后拒绝新的实际启动；在第二次已开始的 STARTING/READY/CONNECTED 状态中，不能因 used 达 2 误杀同一次启动 |
| 超过 1440 min | 当前专用控制功能资格失效；没有充电模型则不能因后来 GRID/DC 恢复偷偷重置 |

注意旧 `DG_START_DC` 实际还作为 DG 持续控制资格：失去 DC 或越过 1440 min 会令 DG 硬件可用性为零，包括已连接状态。这是既有**启动/控制功能资格简化**，不是“真实发动机启动电池没电必然令运行机组停机”的 OEM 结论。纯 `DedicatedDCState` 只管理新启动次数，集成层须继续单列控制窗口，不能把两者混成无限续航。

`DedicatedDCState.request/commit/advance` 均返回新对象。`commit()` 仅接收真实启动身份，重复观察同一 token 幂等；成功与失败实际尝试同样计次；所有候选试探不赋回状态便无副作用。没有本轮新增 DC 补能接口。

## L1/L2 实际等价与有依据的传播

已从原 `DEVELOPMENT68.json` 找到 `matched_factor_id=m21_factor_bc57b8258fae2cc8` 的 L1 `m21_L1_f323b508a1fccd342a61`，与真实 `seen_L2_spring` recipe 对比。全部外生物理输入相同；差异只有类/解析标签、`stage=1/3`、`enable_propagation` 和派生身份/hash。两种 native stage 都使用同一 fault 时钟。默认 `research_stress_proxy=False` 时 `_protection()` 返回空，必要风机/泵、容量及源限制对全部类别相同。因此这个匹配 L1/L2 在同一配置下物理等价，不能把不同 hash 当作不同外生事故。

旧 `m22_seen_L2_spring_01` 与显式代理开的 `m22_seen_L2_proxy_same_01` 事件均只有 120 min 外生 GT_1=0.5 降额和 480 min 解除，没有研究代理 trip。代理开关是物理机制敏感分支，不能包装成同物理条件下的策略比较；没有触发时也不能声称观察到继发故障。本轮 Source05 已实际完成匹配 L1/L2 两个 720 min 过程：177 个原生区间的 ACTUAL_PREFIX 逐字节一致，332 条非命令生成事件逐值一致；只有五项标签/解析/身份元数据不同。证据为审查包 `review/attempts/NATIVE_EQUIVALENCE_FINAL.json`。关闭代理后的该配置物理等价，不是两种独立物理事故。

`RestartState` 只把已存在锅炉复归关系明确为：

```
运行/启动中必要源或流动条件丧失
→ functional_unavailable（已有运行/启动时另记 protective_latch）
→ 已观察上游恢复 + 已到达正许可
→ 连续实际支付既有启动电
→ ready / 清 protective_latch
→ 后续段才可供热
```

普通到达停机为 `dispatch_stopped`，未称永久损坏。源不足或 flow/device 不可用即不进时钟；恢复中再失电清零连续时钟；未到达正许可不启动；已到达停机可在供电丧失前停止运行，避免产生运行中保护锁记录。原 1 min/.5 kWe 只绑定锅炉，不给 EC、泵或风机编造新的复归时间，也不把 unmet 加到 GT 实际出力解释成过流。该依赖过程对 L1/L2 全部一致，类别不能选择是否执行它。

## 接入点与有限参数检查

共同核心在实际边界把当前站支路/真实源/设备条件传给 `RestartState.advance()`；在已到达许可下 `request()`；只在 `_after_actual_segment` 用真实启动电是否足额 `commit()`，然后记录前后状态。`ready=False` 时公共平衡必须关闭蒸汽；不能因为 request 正就加锅炉运行/GT 电力消纳。已 ready 的设备仍须按实际运行电判断 supply 是否存在，不能只看支路布尔值。

针对性完整过程固定同一到达命令时钟，已完成锅炉复归 0/1/5 min 与 GT starter 5/20 kWe 的实际过程，10 kWe 为共同基准。0 min 只标理想下界。原正常 R 敏感过程在支路返回后由 HRSG 覆盖供热，并不约束锅炉热恢复；另登记并执行同一 GT 暂失、站支路暂失条件的锅炉三组过程，按实际付电和出热时钟核验。完整结果见总报告及审查包补充工程表，未按策略胜负选点。
