三、任务 A：建立固定直接电基准，统一需求构造

A1. 先核对现有分解，而非新造临床电表数据

目前可用的基准关系为：
P0/P1/P2：D_ref[g,h] = P{g}_base_e_kW。
P3：D_ref[3,h] = P3_base_e_kW − source_fans_total_kW − source_chw_pump_kW。
A_ref[g,h] = 对应建筑 fan、chw_pump、heat_pump 三项。
E_ref[g,h] = D_ref[g,h] + Σ A_ref[g,h]。

原 heat_pump 为另行增加的热循环泵代理；不得再从 P3 基准扣一次。先独立核验全 8760×4 的数值、单位、非负性及旧边界等值。缺字段或不一致应明确报错，不能 max(0) 掩盖。

字段与文档称“源模型分解的非辅机直接用电基准”，不要称“逐台临床实测负荷”。仍沿用现有 P0–P3 服务分组，不在本轮重新分级。

A2. 需求只构造一次

采用一个清楚、可复用的公共构造口径：
— D_req = D_ref + 明确的直接电冲击。
— A_req = 从当前服务请求、原始参考和既有工程比例近似计算的建筑辅机需求。
— E_req = D_req + Σ A_req。

无直接电冲击的冷需求条件变化必须保持 D_req = D_ref。正负冷量变化按已有工程关系处理，不强制只保留正增量。风机现有 max 比例规则可能使冷量减小时风机仍保持基准，这不要求人为制造对称下降。

不要简单执行 E += ΔA 后，再让新增的聚合电相对旧 E_ref 放大风机。将直接服务驱动、源参考和派生总电分开，防止辅机需求驱动自身。

已有 shock_by_zone 已补过正的辅机增量。把它合并到公共需求入口，或者明确由哪个入口负责一次增量，不能两层各补一次。临床直接电冲击、热冷服务冲击和辅机响应要能够分别追溯。

保留源参考的语义。不要用刚变大的 H/C/E 覆盖原分母，令需求比例重新等于 1，从而抹掉增量。热服务修正进入任务 B 后，也必须明确新请求与原辅机参考如何关联。

对参考为零而当前需求为正的情况，使用现有可证明的备用规则或显式拒绝；不能因除数为零就令有服务却无需任何辅机，也不要任造一个极小除数获得任意大功率。

A3. 计划、可见状态、执行和服务账保持同一需求语义

新版本至少能够逐组逐时段核查：
D_ref、直接电冲击、D_req；
A_ref、A_req 各分项；
E_req；
D_served、A_served 各分项、E_served，以及对应缺供。

实际服务必须满足 E_served = D_served + Σ A_served。请求量不能等同实际用量；辅机故障、供电不足或服务切除时，不得把所需辅机直接当成已经支付。

故障改变可用设备与实际服务，不改变事件发生前已经确定的原始请求。不要重新执行 direct = aggregate − actual_aux 后把本应缺供的直接电需求缩小。

所有重要路径都必须调用新口径：正常、条件冷扰动、医疗需求冲击、公开入口、计划器、执行层和只读复算。允许保留有明确身份的 legacy 入口以重放旧结果，但新的公开 V28 不能悄悄走旧缺陷路径。

A4. 保持故障归属及厂站支路正确

fan_component_*、源 priority_shares、公共风机可用比例与放大后的风机功率须一致。不能只重写总 fan 字段却保留不相容的组件分配。

建筑冷水分配泵、热循环泵与能源站转换设备支路不同。原 EC 的综合系数已包含登记的冷却塔/冷凝侧泵假设；EC、ABS、GT 启动、锅炉及储能专用泵等原支路不得再次混进 D_ref/A_req。任何必要的边界迁移必须列明同时移出和移入的位置，证明只计一次。

B2. 请求、交付、源输入三者分开

WaterUse Heating Rate/Heating Energy 描述交付侧热量，不自动等于目标请求。按本版本引擎的真实定义核实所选变量，先查看原 SQL 的完整 ReportDataDictionary。V27 精选冷量字典不足以证明整个 SQL 没有水变量。

请求取水量应来自有效峰流×排程×适用倍率；与实际 Total/Hot/Cold 流量对照。目标有用热采用请求流与目标/进水条件，实际交付采用被接受时段的原生能量或严谨积分。水密度、比热/焓、区域倍率、日型、节假日、DST 和标准时端点均须说明并只应用一次。

如需用 Q_target = m_requested × cp × max(T_target−T_inlet,0)，请明确这是对应取水服务的目标有用热，不是整个供热系统的输入。不能用已经受限的实际总流代替请求流来消除未满足服务。

若存在回收或同水流的上游预热，分别记目标服务与净源侧需要；不能机械叠加全温升。对交付大于目标或储能释放的时段保留原始有符号能量，并另外计算定义清楚的未满足服务，不能为了年度差额直接裁掉所有反向值。

本任务包的工程筛查：30 末端目标约 124.45 MWh、旧交付约 121.34 MWh、laundry 目标约 118.64 MWh、booster 增温约 7.07 MWh，只能帮助优先排序。它使用 rho=1000、cp=4180 工程常数，未认证有效倍率和全部原生水物性，不得写入正式需求替换旧表，也不得把 3.11 MWh 写成已验证的年度欠供。

B3. 独立 laundry 与 booster 必须作出有依据的处理

Laundry：源对象为天然气、82.22℃目标、独立取水排程；不属于现有 WaterUse Heating Rate 求和。核验其用水侧目标/交付、容量、热损失和燃料。

Booster：源对象为电热、60→82.22℃；其电耗已进入建筑 WaterSystems 电边界。核验具体电分表和同一股水的 60℃预热归属。没有管网节点及流量对应证据时，不得默认它已经被其他用水对象覆盖，也不得默认 60℃进水免费。

每条服务选择一个正式边界，必要时保留另一个仅作以后备选：
— 保留本地热源：保留已存在的电/燃料支路；热服务只在台账中解释，不再作为中央新热量请求重复求和。明确其源能耗、储能及可用性范围。
— 改由中央供应：必须有热源温度能力、连接/转换及容量依据；同步移除被替代本地能耗，交代储能与损失。不允许只加热需求、原电或燃料仍暗中继续供给。
— 明确排除某服务：说明服务范围和缺口，不能继续声称完整覆盖全院。本轮能由现有源和一次观测解决的部分必须继续解决，不能把“排除”当规避已有具体问题的捷径。

缺少改接依据时默认保留原本地设备；先完成服务与能源边界闭合，不新造免费换热器或无容量限制的 82℃中央供热能力。若 booster 预热在源模型本身没有物理上游，做出明确的工程边界决定：建立单列、可追溯的上游热请求并给出假设和一次计量关系，或限定该本地服务不在当前中央保供资格内。不能给出既不计能又宣称充分供应的结果。

B4. 独立热水器做设备能量账

按实际变量符号核对：有效燃料/电加热、源侧换热、入罐寄生热，与用水侧交付、储能变化、散热及其他损失之间的关系。燃料输入乘效率后的有效加热与其燃料输入不能当两份热量；Heater Heating、Use Side Heat Transfer、Total Demand Heat Transfer 不能全部相加。

采用真实被接受的系统/区域时段和精确时间区间。必要对象可以保存 Detailed，在本地聚合成可携带的小表。跨小时按真实时长积分，不能对不等长子步等权平均；不能将小时平均流量与小时平均温差直接相乘而忽略二者的共同变化，除非验证小时内恒定或给出受控误差。内部迭代警告不作为服务时间序列。

先用原提取器复现原四张 CSV：优先字节一致，随后检查时钟、列及数值；发现不一致必须定位来源。不能把补输出导致的新物理轨迹或改过的基线直接用作“观测”。若精确构建确实不可用，使用兼容构建也要明确该变化并作数值同等性验证，不伪称同一运行。

只读保留原源与旧四表。新增观察通过同等性检查后，才生成候选目标服务输入。全部必需 Key、时段、单位、倍率和求和关系都应检查，缺项不得默认零。

SQL false 完成标志只做有边界诊断：记录原值与 SQLite typeof、原生读取及 reader 转换、引擎版本、退出码、日志、完整时钟，并对比新观察结果。证据足够即可解释，不以此开展无关引擎开发。

本轮以一次有效年度观察为目标。配置/输出错误允许修复后必要重试，全部尝试如实记录；没有具体剩余缺口时不再做第二套物理年度试验。不得把“额度足够”理解为必须多跑。

七、把热边界修正真正接入模型

1. 若核实存在目标/交付差异，且该服务属于当前中央供应边界，生成独立的新需求输入；旧实际交付曲线仍留作来源对照。不要用附加标签继续将低于目标的原交付直接当完整请求。
2. 空间供暖、普通热水、保留本地高温热服务保留清楚分量；不必发展全套水温动态，但热级别和接口能力必须如实登记。
3. 更新与实际热服务相关的需求字段、等级汇总、来源追踪和 fan_independent_heat_bound。热水可不依赖空气风机，但仍受真实热源/所需水泵等约束；新增独立热水不应被误当成需送风的空间负荷。沿用已有工程近似时，明确其适用范围。
4. 新热需求对辅机的影响使用任务 A 的唯一构造口径，不能额外在热适配层再补一次电。若保留本地 booster，电仍在正确直接电基准中；若明确替代，源电扣除必须可追到对应分表，不能从总电任意估扣。
5. 对冷机/塔曲线警告，只判断是否通过供水限制使所导出的盘管交付低于源建筑目标服务。若没有相关未满足证据，保留该有限结论；若有证据，定位受影响对象/时段、给出来源使用限制和一项有依据的后续修正。不能仅因未满足小时为零便宣布水力、湿度或洁净度全部合格，也不能无依据把冷量乘一个经验修正率。

八、最终运行安排：只解决剩余的具体风险

推荐执行顺序：
阶段 A：边界修正 → 原热版本下 W1 四例 → 最少临床冲击及辅机故障回归。
阶段 B：原 SQL/必要一次观察 → 热服务台账 → 新候选输入 → 明确采用的 V28 需求版本。
阶段 C：新输入若影响运行，使用一个共同版本做最少受影响回归，优先完整 N/F/D/FD 四例，并覆盖实际取水/洗衣活动时段。若原四例窗口不含需核验的服务，应选一个说明理由的共同窗口，避免空测。

通常约 6–10 条新的实际 IES 轨迹足以完成主验收，允许为明确失败或尚未覆盖风险补充少量运行。它不是必须凑足的配额，也不是发现缺口后被迫停止的硬上限。新增超过计划时说明具体原因，不能自动升级为全年 IES 或完整历史矩阵。

不同阶段保持输入身份分开；任务 A 的单独影响与任务 B 的输入修正分开报告。不要做“旧新电边界×旧新热边界×全部策略×所有历史工况”的机械全排列。

同一组对照保持全物理初态、库存、已有机组状态、合法控制历史、源负荷版本、信息规则和场景事件一致。不能只匹配可见的几项库存，忽略延迟队列或已经启动的设备。换输入后的合法当前需求变化不应被误判为物理初态不公平。

记录真实启动、运行和服务，采用实际分段积分。服务未中断时恢复时间为不适用；存在微小原始缺口则保留原值与原工程判定，不改阈值制造通过。保留有符号变化、期末状态和库存差，短窗费用差不外推长期收益。

主修正完成后执行仓库要求的默认完整测试一次及干净公开入口。修改后若具体失败再做相关复验，不反复无目的跑全套。独立审阅应针对原始服务/能量账和实际调用路线，不只看自己生成的“pass”标签。
