一、直接结论

V27 比 V26 有实质进展。上一轮“为了少开燃机，先牺牲费用目标”的问题已经做了真实修正：改变了运行命令、支付了启动电、产生了实际供能与费用变化。这一项可以收口，不需要再为了形式上的更强名称反复重排所有运行偏好。[E3]

当前模型适合描述：在既定设备能力、建筑负荷代理、运行准备规则和故障边界下，医院能源站如何供电、供热、供冷，以及选定工况中的服务缺口、费用和条件排放。它已经具备较好的来源追溯和实际过程核算能力；本次检查未发现新的主供能守恒、启动提前出力或费用重复付款问题。[E1–E3]

但“每一步按输入算对”还不等于“输入完整表达医院需要的服务”。下一轮最需要改的是两个具体边界：
1. 非辅机直接用电应有独立基准，新增建筑风机、水泵用电不能靠缩小直接用电来抵消。
2. 热需求应分清目标服务、实际交付和设备输入，并清点普通热水、独立洗衣高温热水、电热增温器的能源归属。

建议把 V28 定为“需求边界闭合版”。它应完成代码和输入的实际修正，并重跑受影响的少量工况。不要只把原结论改成条件成立或未知，随后继续保留同一缺陷。

本轮没有给整个模型打一个百分比。代码测试数量、几个场景没有中断，都不能换算成“模型完成了 95%”。更有用的判断是：哪些物理链可以使用，哪些服务边界还缺一段，以及下一轮用什么证据关闭它。

三、已经做对、可以保留的部分

3.1 运行目标顺序确实修正了

新的 C_reliability_then_cost_v27 把“总在线燃机台数尽量少”放到原费用目标之后。服务、准备、调节一致性和第三机备用相关目标仍保留，费用向量及原费用锁容差未改变。旧方案仍可明确调用，但不会把旧的台数等于 0 的锁带入新方案。[E3]

因此，准确名称是“在既定服务和运行准备规则下，费用先于总台数偏好”。它并非无条件的全时域经济最优；也没有必要因此马上打开所有软目标的消融研究。

新顺序节省 6.877046659 USD2001；条件排放增加约 175.228 kg。两台机组在 90–100 分钟合计消耗 20 kW 启动电，期间实际出力为 0，100 分钟后才供能。费用改善不是靠免掉启动过程得到的。[E3]

这组结果有两个使用限制。第一，费用下降伴随条件排放上升，不能同时宣布既省钱又减排。第二，两分支末端燃机状态不同，虽然柴油、UPS 和蓄冷库存相同，也不能把后 90 分钟节省直接推广为长期等终态收益。A1 容器的前 90 分钟仍来自旧策略，不能把该容器总费用当作全时域新策略结果。[E3]

3.2 新完整四工况是有效的有限验证

正常 N、设备故障 F、需求增长 D、二者组合 FD 已从同一初态完整运行 0–180 分钟。故障前 15–30 分钟，GT2 实际约 125.208 kW，故障不是施加在原本闲置的设备上。30–90 分钟只改变 GT2 本体可用性；HRSG2 本体健康但失去热源，其他机组余热未被错误清零。[E3]

四工况实际能源费依次为 115.0911、118.5920、115.5017、119.0413 USD2001；热、冷未满足能量为 0。原始微小电缺口被保留，按已有工程判定没有关键服务中断，故恢复时间应为“不适用”，不应强造恢复曲线。[E3]

这支持所测负荷、可用外网和设备条件下的过程正确性，不代表已经验证外网全停、长时间燃料耗尽、全年所有故障或全院温湿度与洁净度达标。

3.3 年度来源追溯比上一轮清楚

V27 找回了实际使用的 26.2 派生 IDF、提取器、日志和来源元数据，并保存了原 SQL 重导四张 CSV 后字节一致的记录。包内年度时钟连续，8 盘管冷量求和与输入逐小时一致，年冷量为 3,324,738.363451 kWh；14 区的条件变化映射也能独立复算。[E5]

但大型原年度 SQL 不在本压缩包。本次独立验证的是保存表、源文件和重导记录，没有在这里重新读取那两份原年度 SQL。源表可重现与源建筑物理充分可信是不同的验收问题。

四、下一轮必须修正的第一项：直接电与建筑辅机不能互相抵消

4.1 当前问题的具体形式

现有 service.py 先按电、热、冷相对参考负荷的比例计算建筑风机、冷水分配泵和热循环泵所需电量，再用下面的方式确定直接电需求：

直接电需求 = 聚合建筑电需求 − 建筑辅机需求。

V27 的条件冷需求适配只改变冷量，聚合建筑电需求保持原值。于是冷量增加、建筑辅机增大时，直接用电在计算中自动减少。这套定义内部仍然可以守恒，但没有表达“其他直接用电不变时，额外制冷服务需要多耗多少电”。[E4]

不能把这个问题泛化为所有需求突增路径都错。已有 shock_by_zone 路径会补入正的辅机电增量。下一轮统一入口时，反而要防止它被补两遍。[E4]

4.2 本次差额有多大

同一 14 小时 W1 窗口，两种策略的新增建筑辅机需求都是 15.3499828344 kWh，直接电分解恰好减少相同数值。其中 P3 为 15.3108284946 kWh，占约 99.75%；P0–P2 合计很小。最大一小时差额为 10.1331 kW。[E4]

这是相对“固定直接用电”命题的需求差额，不是本次新求解得到的失供能量，更不是实测临床用电被削减的证据。该小时原条件轨迹的 C/M 购电约 618.106/780.329 kW，均未达到 850 kW 上限，也不能据此推断一定新增缺电。[E4]

站内制冷转换电已经增加约 30.59/30.68 kWh，这部分已在原模型正确支付。下一轮只补正确的建筑需求关系，不能把站内 EC、ABS 以及已包含的塔和冷凝泵耗电再加一次。[E4]

4.3 不必等逐台实测电表才能修

已有 auxiliary_allocation_8760.csv 和 M22 环境分解足以得到源模型的非辅机直接用电基准：
P0–P2：D_ref = 对应 P_base_e。
P3：D_ref = P3_base_e − source_fans_total − source_chw_pump。

热循环泵是原代码另行追加的项目，不能再次从 P3 中扣除。全部 35,040 个组小时直接用电基准均为非负。它应称“源模型分解的直接用电基准”，而不是医院逐台实测临床电量。[E4]

修正后的关系应为：
D_req = D_ref + 明确的直接电需求变化；
A_req = 根据当前服务需求、源参考及既有工程关系计算的建筑辅机需求；
E_req = D_req + 各项 A_req。

冷需求单独变化时，D_req 固定。需求与实际供给分别记录；发生故障时，可以少供、记缺口，但不能靠重新定义需求把缺口消掉。

实施重点有两个：新增辅机电不能再通过“新的聚合电/旧的聚合电参考”反复抬高风机需求；风机分组件及其优先级归属必须继续一致，不能改功率字段后破坏原故障映射。[E4]

五、下一轮必须修正的第二项：热服务范围与热量定义

5.1 原交付热量不能自动当成目标服务需求

原提取式为：供热输入 = 各供暖盘管交付热 + 各 WaterUse:Equipment Heating Rate。

EnergyPlus 对后一个量的定义来自实际热水流量及热、冷水温差；当热水温度或流量不足时，末端混合温度可以达不到目标。因此它是重要的交付记录，却不自动等于达到目标温度所需的完整服务量。[R1]

下一轮应分列“按排程请求多少水、目标温度多少、实际得到多少水及温度、实际得到多少热量”。若实际流量已经受限，也不能只用实际流量反推目标需求，否则会再把未满足部分抹掉。末端用水热只是供热账的一部分，不能拿它替代空间供暖、再热、罐体储能和损失。

原 30 个 WaterUse 对象目标均为 60℃。独立工程筛查采用明确的水密度与比热常数、源排程、补水温关系和源时钟，得到约 124.45 MWh/年的目标有用热，而旧输入中的交付热约 121.34 MWh/年。约 3.11 MWh 的差额只是筛查线索，尚未核实原生水物性、有效倍率与接受时段流温，不能作为已证实的年度欠供。[E5]

5.2 独立洗衣热水器是值得优先清点的边界

实际 IDF 还有 SWH Laundry Water Heater：燃气设备、目标 82.22℃、独立取水排程，没有接入上述 WaterUse 末端热量求和。按源排程做量级估算，其目标有用热约 118.64 MWh/年，与当前全部普通热水交付热处于同一量级。[E5]

这不是已经证明“年度总热需求精确少算 118.64 MWh”。若研究明确保留该本地设备、将其服务划在能源站调度边界之外，就不应机械塞进中央供热；但它必须在全院服务范围、燃料、费用和排放归属中说明，不能完全消失。

应作出一个可以实施的边界选择：有中央连接和供热温度能力依据时，纳入中央系统并取消原本地重复供能；否则保留本地设备并单独核算。现阶段缺少连接证据时，优先保留原物理配置。82.22℃高温服务不能仅凭模型存在一个名为“steam”的热量变量便视为已经满足。

5.3 电热增温器存在另一种风险：重复计算

SWH Booster E Water Heater 为 3 kW 电加热，源设定是从 60℃升至 82.22℃。其增温目标热的工程筛查约 7.07 MWh/年；电耗已进入原建筑 WaterSystems 电边界。若又把相同增温热加入中央供热而保留原电耗，将重复付能。[E5]

还要查清这股水的 60℃预热由谁提供。不能没有连接证据便认定已包含在 30 个末端中，也不能默认免费获得 60℃热水。独立热水器本来就可以只靠取水排程运行而没有管网节点，不能仅靠对象名称猜测能量连接。[R2]

每个本地热水器应有两张账：用水侧的目标与交付服务；设备的电/燃料输入、有效加热、储能变化与散热。源燃料输入、罐内加热、用水侧放热是不同位置的量，不能相加作为“总需求”。

六、年度警告应如何处理

实际警告次数约 2,283 万：热水目标温度高于供温约 2,204 万，冷机曲线域约 76 万，冷却塔域约 3.5 万，另有少量非 recurring 记录。这是部件及内部迭代调用的累计次数，不是欠供小时数、独立故障数或可以直接积分的热量。[E5]

因此不能只因数字大就判整年无效，也不能因 0 Severe 就宣布全部目标服务满足。

热水方面，使用被接受时段的流量、目标/混合/冷热水温和原生能量输出。先查原 SQL 完整变量字典；若必要字段原本没有保存，授权一次保持物理对象、容量、排程、曲线、天气和版本不变的年度补输出运行。先证明旧四张边界表仍可重现，再采用新增观察量。

供冷方面，原冷机和塔的电耗在 IES 中主要被替换，不能直接把源冷机电耗误差当成 IES 的同额误差。真正需要检查的是：供水温度/流量/容量限制，是否降低盘管交付并造成房间设定点未满足，进而把受限后的交付错误当作完整需求。下一轮只追这条主服务通路，不要求清除所有警告或重建水力系统。[E5]

SQL Completed/CompletedSuccessfully=false 与 .end 成功、全年时钟完整之间仍有记录冲突。应查原字段类型、读取转换、退出码和同版本行为。它值得解释，但不能单独据此认定全年失败，也不能无依据宣布是已知无害行为。

七、现在不应扩大为主任务的事项

1. 60 分钟启动撤销：真实顺序是旧命令被最新到达命令替代，随后当时新生成的命令取消尚未发生实际区间的启动；不是过期命令覆盖新命令。该次取消未支付实际启动电，75–85 分钟重新启动才付电。现有证据没有证明服务受损或该撤销必然不经济，不应立即增加不可取消启动的硬约束。后续若出现重复撤销、已付启动功浪费或服务拖延，再做一个同状态核查即可。[E3]
2. 已退出资格的动态冷水、温度基线与表面模型：本轮仍未恢复资格，不重复拟合、不把 MinPlant8 当年度真实修正。
3. 更多算法、MPC、机器学习预测、大规模策略矩阵：目前主要缺口在需求边界，增加控制复杂度不能修好边界。
4. 全院实测标定、洁净度验证、设备选型优化：属于以后增强真实工程适用性的工作，不是完成本轮两个修正的前置条件。

八、建议的 V28 顺序和完成标准

第一步：直接修改公共需求构造与服务核算，完成 D/A/E 分开。验证零扰动逐小时等值、正负冷量变化、既有临床冲击只加一次、辅机故障不会缩小原请求。重跑同一 W1 的 C/M×原冷/条件冷四例，继续采用原热需求以便辨认该修正的单独影响。[E4]

第二步：完成热服务台账。检查原 SQL；必要时补一次年度观察；核实 30 个末端的请求/实际、独立 laundry 和 booster 的服务及能源归属、预热和储能损失。能由现有证据形成的新需求输入，就生成独立候选版本并真正接入公开运行入口，不只写未知。[E5]

第三步：在一个冻结的新需求版本下运行最少的受影响回归。优先复用正常、故障、需求增长和组合工况，必要时选含实际取水时段的窗口；不在四案中混用输入版本，不为了展示差异而人为制造故障后果。若只改报表且运行需求未变，就不重复无变化的运行。

本轮完成的标志是：
— 任一时段，直接电需求、建筑辅机需求、总建筑电需求可独立核对，故障不能通过改需求隐藏缺口。
— 每条热水服务有明确请求、交付、能源来源、温度要求与是否纳入中央调度的说明；同一服务不漏账、不双算。
— 新结果按真实供能、启动、能耗、费用、排放和初末库存核算，允许结论变好、变差或保持不变。
— 模型在选定范围内完成修正即可收口，保留仍不具备的年度物理真值、实院标定和室内环境资格；不以取得这些更大资格为由无限追加本轮工作。
